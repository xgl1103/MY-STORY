# 【生活娱乐赛道】My Story——把每日日记变成一部由自己主演的 AI 连载小说

## 1. Demo 简介

### 它是什么

**My Story** 是一款本地优先的 Web App：用户写下当天的日记，选择故事世界观与行为映射，AI 就会把真实经历续写成一章以用户为主角的连续小说。

它不是把日记简单改写成一段文案，而是让“记录今天”变成“追更自己主演的故事”。

### 面向谁

面向觉得普通日记枯燥、难以坚持的学生与上班族，也面向喜欢奇幻、修仙、克苏鲁等题材，希望获得专属故事体验的小说爱好者。

### 核心功能

1. **引导式日记记录**：用户可按当天发生的事件写日记，并标记学习、工作等行为；降低“面对空白页不知道写什么”的记录门槛。
2. **日记到连载小说的映射生成**：系统将当天事件映射进选定世界观，结合此前章节与人物线索，生成连续的小说章节；生成结果会展示日记事件与故事情节的对应关系，方便用户确认。
3. **本地优先与用户自带 API Key**：日记、章节和故事状态保存在用户浏览器本地；用户自行配置兼容模型 API Key 后即可生成内容，Demo 不依赖我方后端服务器。

## 2. Demo 创作思路

我自己写日记时，常常觉得像在完成一项任务：记录了，但不期待明天继续写。另一方面，读小说时又会想：如果主角就是自己、剧情能跟着今天真实发生的事继续发展，会不会更有代入感？

因此我尝试把“日记”从终点改成故事的输入。用户今天学习、通勤、运动、遇到的人和烦恼，都可以在不同世界观里变成修炼、冒险、调查或人物关系的推进。这样，记录不再只是回顾，而是明天继续追更的伏笔。

我选择“生活娱乐”赛道，是因为这个项目首先解决的是记录习惯的趣味性和持续性问题：不要求用户写得像作家，只要真实地写下今天发生的事，就能获得一段属于自己的连续故事。

在实现上，我把本地存储放在第一位，避免用户日记必须上传到我的服务器；AI 调用采用用户自带 API Key 的模式。这样既降低 Demo 的部署成本，也让用户对自己的私密日记有更多控制权。

### 开发中遇到的问题与解决

#### 问题 1：旧版将长内容误判为生成失败

在一次真实 API 生成测试中，我发现旧版质量门禁把“正文超过 1200 字”直接判为失败；即使模型已经生成了 1565 字的完整内容，界面仍会提示 `E007`，造成用户无法确认和保存章节。

我随后将逻辑从“硬性最大字数拦截”调整为“至少 800 字、事件覆盖、句末完整性”的质量校验：内容过长不再被直接拒绝，而是让模型自然扩展；同时保留对过短、事件遗漏和半句结尾的补写/续写处理。修改后重新完成真实生成、确认保存与刷新读取验证，当前公开体验版不再保留 1200 字上限。

#### 问题 2：早期 Agent 记忆不连贯，长线伏笔容易丢失

早期版本主要把最近几天的原文拼接进 Prompt。短期衔接尚可，但随着故事推进，会出现人物、物品和地点的状态前后不一致，较早埋下的线索被遗忘，甚至当天日记也容易被大量历史上下文淹没的问题。

为此，我将“让模型自己记住全部内容”改为**多层记忆架构**：

1. **章节摘要记忆**：为已完成章节保存摘要，提供宏观剧情进展；
2. **世界观 RAG**：按用户选择的世界观、途径和关键词检索设定，避免生成内容偏离规则；
3. **动态剧情 RAG**：从已生成的历史章节中按当天事件、人物、地点和行为映射检索相关片段；优先 FTS 检索，必要时降级为关键词匹配，使远距离剧情也能被召回；
4. **实体档案**：章节确认后提取角色、物品和地点及其当前状态，保证称谓、关系和道具状态一致；
5. **未回收伏笔池**：保存每段新埋下的悬念及其优先级，并在后续章节生成时提示模型自然回收；
6. **最近原文窗口 + 当日日记硬约束**：保留最近章节保证语气和场景衔接；把当天事件清单放在 Prompt 最后，并在生成后校验关键词覆盖，确保“今天的真实经历”不会被历史记忆挤掉。

章节定稿后，系统会再执行一次轻量记忆提取：更新实体档案、记录新伏笔，并识别已经回收的伏笔。这样，记忆不再只是越来越长的聊天记录，而是可检索、可更新、可验证的故事状态；长篇连载能兼顾近期连续性、历史线索和当天日记的真实性。
